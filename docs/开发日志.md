### 2.2 ADR-002：纯启发式规则，不调用 LLM

- **决策**：纯启发式规则（regex / 阈值 / 启发式分类），不调用 LLM [source:agents-md:AGENTS.md:17]。

- **后果**：依赖限制为硬约束（Python 标准库 + `langdetect` + `openpyxl` + `chardet`），重型库 `PyQt` / `litellm` / `asyncio` / `playwright` 显式禁用 [source:agents-md:AGENTS.md:56-59]。

### 2.3 ADR-003：OCR 默认 flag-only 先观察

- **决策**：OCR 默认模式为 `flag-only`（仅标记污染分数，不修改内容）[source:omo-plan:corpus-cleaner.md:8] [source:agents-md:AGENTS.md:85]。
- **理由**：四级模式逐级递增侵入性（flag-only / clean-mark / clean-light / clean-aggressive），默认最保守；先观察污染程度再决定是否清洗 [source:omo-plan:corpus-cleaner.md:49]。
- **后果**：`flag-only` 完全语义安全；需要清洗时升级至 `clean-mark`（`[?]` 占位保语义）；下游有修复能力时再升至 `clean-aggressive` [source:agents-md:AGENTS.md:81-88]。

## 3. 踩坑与修复记录

### 3.1 safe_filename() strips Unicode — 与 plan 矛盾

- **问题**：`utils.py:safe_filename()` 将非 ASCII 字符（Arabic/CJK/Cyrillic）替换为 `_`，但 plan Section 5 Stage 5 明确要求 "Unicode 字符保留（Windows 原生支持）" [source:omo-notepad:issues.md:5-9]。
- **根因**：T1 阶段选择保守策略 — `safe_filename()` 设计为 ASCII-only 兜底函数，担心 Windows 文件名中 Arabic/Cyrillic/CJK 可能导致下游问题 [source:inference:project-dev-docs/task-3/corpus-mining-notes.md:131-133]。
- **修复**：T8（Renamer）修正。`_sanitize()` in `renamer.py` 使用 `_RE_LATIN = re.compile(r"[A-Za-z]+")` Latin-only regex 进行小写化，仅匹配 ASCII 字母（无 `re.UNICODE` flag），因此 Arabic/Cyrillic/CJK 字符通过而不被小写化；`safe_filename()` 保持为保守的 ASCII-only 兜底 [source:omo-notepad:issues.md:8] [source:inference:project-dev-docs/task-3/corpus-mining-notes.md:133-135]。
- **位置**：`corpus_cleaner/renamer.py:_sanitize()` / `corpus_cleaner/utils.py:safe_filename()`。
- **状态**：已修复，Unicode 文件名在生产运行中正常生成 [source:inference:project-dev-docs/task-3/corpus-mining-notes.md:134]。

### 3.2 Null-byte 污染破坏 reporter Excel 输出

- **问题**：真实 AR 语料文件内容含 `\x00`（null bytes），可能来自 OCR 输出损坏或原始数据源的编码 artifact；通过 `_extract_title()` → `_sanitize()` → `generate_new_name()` 进入 `new_name` 字段；`reporter._sheet_file_details()` 写入 openpyxl 单元格时触发 `IllegalCharacterError` [source:omo-notepad:issues.md:10-23]。
- **根因链**：
  1. 真实 AR 语料文件内容含 `\x00` — OCR 输出损坏或编码 artifact [source:omo-notepad:issues.md:12]
  2. `renamer._sanitize()` 仅处理 Windows 禁用字符 + ASCII Latin 小写化，不处理 null bytes 或 C0 控制字符（U+0000-U+001F）[source:omo-notepad:issues.md:15]
  3. Null bytes 通过 pipeline 传播至 `new_name` 字段 [source:omo-notepad:issues.md:16-17]
  4. `reporter._sheet_file_details()` 写入 openpyxl → `IllegalCharacterError` [source:omo-notepad:issues.md:18]
- **示例失败文件名**：`misc_بسم_ا\x00_الرحمن_الرحيم_043_S.md` [source:inference:project-dev-docs/task-3/corpus-mining-notes.md:146]。
- **修复方案**：`renamer._sanitize()` 应剥除 C0 控制字符（U+0000-U+001F，保留 `\t` `\n` `\r`）；或在 `reporter._write_excel()` 单元格写入前做防御性 sanitize [source:omo-notepad:issues.md:21-22]。
- **状态**：Known（截至 notepad issues.md 最后更新 2026-07-20 T12）。合成数据测试全部通过；真实数据测试标记为 `xfail` [source:omo-notepad:issues.md:20]。
- **影响**：真实 AR 数据上 pipeline 无法完成，直到修复应用 [source:omo-notepad:issues.md:23]。
- **位置**：`corpus_cleaner/renamer._sanitize()` / `corpus_cleaner/reporter._sheet_file_details()`。
- **后续线索**：T3 挖掘笔记记录 T13 已实施修复（renamer + reporter 双重防御）并在 T14 生产运行（3280 文件）验证通过 [source:inference:project-dev-docs/task-3/corpus-mining-notes.md:147-151]。但 notepad issues.md 未同步至该状态，本文档以 notepad 为权威源。
